# AI 工作流案例：讓 AI 寫機率模型，再用獨立的方法檢查它

## 30 秒看完

- **做什麼**：從一段文字寫的老虎機規則開始，做出規格、理論 RTP、模擬器、統計驗收和回歸測試。
- **AI 負責**：大部分的程式碼（Claude Code、Cursor）。
- **我負責**：定規格和計算口徑、自己推導公式、決定「怎樣才算對」。
- **核心原則**：AI 說「我寫好了、結果正確」不算數。每個數字都要用另一條獨立的路算出同樣的答案。
- **成果**：理論 RTP 96.6506%，三種方法算出來精確相等。5,292 萬局模擬落在 95% 信賴區間內，下面 3 個 AI 寫錯的地方都在上線前抓到。

## 流程：AI 寫，我把關

| 步驟 | AI 做的事 | 我做的事 |
|---|---|---|
| 1. 規則變規格 | 把文字規則整理成設定檔（賠率表、線型、Wild／Scatter、免費遊戲） | 補上**計算口徑**：RTP 的分母是總押注；免費遊戲贏的錢算在觸發它的那一把 |
| 2. 算理論值 | 寫計算理論 RTP 的程式 | 先自己在紙上推公式，再逐行對照程式有沒有照公式寫 |
| 3. 寫模擬器 | 寫 Python 模擬器 | 要求只看規格、用 C++ **重寫一份**。兩份不共用程式碼，一份寫錯另一份不會跟著錯 |
| 4. 交叉比對 | 寫比對程式 | 定好標準：理論值和窮舉結果要**完全相等**；同一個盤面，Python 和 C++ 算出的獎金要**一模一樣** |
| 5. 判讀結果 | 算信賴區間和 z 值 | 依獎金的波動大小決定要跑幾局，並確認 20 次獨立模擬中大約 19 次涵蓋理論值 |
| 6. 回歸測試 | 寫自動測試 | 決定哪些數字要鎖住；以後改參數，一定要重跑、看過報告才更新 |

## AI 寫錯的地方（實際遇到的）

### 1. 變數被偷偷改掉（程式錯誤）

- **AI 寫了什麼**：C++ 判斷「這一把有沒有中獎」時，用的是 Scatter 數量這個變數。
- **哪裡錯**：這個變數在免費遊戲迴圈裡會被重複使用。等到要判斷的時候，裡面裝的已經是「最後一次免費遊戲」的 Scatter 數，不是主遊戲那一把的。
- **不修會怎樣**：命中率會算錯，而且只在觸發免費遊戲的那幾把出錯，平常很難注意到。
- **怎麼發現**：審程式時追這個變數在哪裡被改過。就算當時漏看，C++ 的命中率也會和窮舉算出的精確值對不上。
- **怎麼修**：觸發的當下先存成一個獨立的 `triggered`（是否觸發）。

### 2. 公式偷藏了一個假設（模型錯誤）

- **AI 寫了什麼**：用「這一軸的畫面上出現 Scatter 的機率 = 3 × Scatter 個數 ÷ 輪帶長度」計算觸發機率。
- **哪裡錯**：這條公式只有在「同一軸的畫面最多只會出現一個 Scatter」時才成立。如果輪帶上兩個 Scatter 靠太近，可能同時出現在畫面上，公式就會算錯，但程式裡沒有任何地方保證這件事。
- **不修會怎樣**：某天有人改輪帶，把兩個 Scatter 排得太近，理論值會悄悄變錯，卻不會有任何錯誤訊息。
- **怎麼發現**：自己推導公式時，回頭問「這條公式什麼情況下才成立？」
- **怎麼修**：產生輪帶時規定 Scatter 至少間隔 3 格，載入設定時也會檢查，不符合就直接報錯。

### 3. 兩種規則剛好算出一樣的答案（規格模糊）

- **AI 寫了什麼**：規格只寫「Wild 可以替代其他符號」，AI 就照自己的理解寫了一種算法。但這句話至少有兩種合理的解讀：「取 Wild 本身賠率和替代後賠率中較大的」，或「把 Wild 當成第一個不是 Wild 的符號」。
- **哪裡錯**：在這份賠率表下，兩種解讀剛好算出一樣的結果，因為 Wild 的賠率最高。換一份賠率表，兩種解讀就會不一樣，而規格沒說清楚該用哪一種。
- **不修會怎樣**：現在測不出來，等到調整賠率時才會出錯。
- **怎麼發現**：寫單元測試時，刻意找會讓兩種寫法結果不同的盤面。例如 `W W W L4 L4`：Wild 三連賠 50，當成 L4 五連只賠 40，應該要取 50。
- **怎麼修**：規格明文寫出規則，並把這些邊界盤面加進測試。

## 其他不是 AI 寫錯，但值得一提的

- **參數一開始就離目標很遠**：第一版輪帶的理論 RTP 只有 67.7%，目標是 96% 左右。因為理論值幾秒就算得出來，所以直接用理論模型去調符號配置，不用靠反覆跑模擬來試。
- **驗收流程本身也要測**：我故意在模擬器裡放進 4 種常見 bug，確認驗收流程每一種都抓得到。例如抽停輪位置時少抽最後一格，RTP 會偏高 2%，z 值 +7.7。詳見[驗收報告](../reports/v1.0.0/report.md)第 7 節。

## 同樣的方法用在真的遊戲上

在我自己的 Godot 遊戲《天魔劫》裡，有一個抽獎轉輪「天機輪」。我照同樣的方式做了模型，並和遊戲的程式碼直接對照。

這次抓到的錯比較隱蔽：**AI 寫的模型把「門派共鳴」的三張候選當成彼此獨立，但遊戲實際上是從同一門派不重複抽**。轉輪判定和觸發機率都和遊戲 100% 一致，所以一開始沒發現。

後來回頭讀遊戲的抽卡程式，才注意到這一點。於是在測試裡加上「讓遊戲用固定種子實際抽候選」的對照：舊模型的 z 值是 −7 到 −16，修正後在 ±1.3 以內。

完整說明：[天機輪數學驗證報告](https://github.com/Benny021018/wuxia-rogue/blob/main/docs/shrine-math/report.md)

## 我從這些經驗得到的做法

1. **規格自己寫**，尤其是計算口徑和邊界情況，AI 最容易在這裡自己腦補。
2. **公式自己推一次**，並寫下它成立的前提。
3. **重要的計算至少要有兩條獨立的路**（解析計算、窮舉、另一種語言重寫），而且答案必須完全一樣。
4. **測試要刻意去找會讓結果不同的情況**，不能只測正常情況。
5. **模擬結果用信賴區間判斷**，不用「誤差小於 0.5%」這種固定標準。

## 成果

- 一個指令（`python validate.py`）約 75 秒跑完 11 項驗收，報告會記下參數版本、設定檔雜湊、亂數種子和局數。
- 16 項回歸測試約 5 秒。
- 理論 RTP 96.6506%。5,292 萬局模擬的結果是 96.672%，95% 信賴區間 ±0.100%，涵蓋理論值。
